# CLAUDE.md

이 파일은 Claude Code가 `sosang/`(소상공인 경영진단) 아래에서 작업할 때 따라야 할 지침이다. 상위 폴더(저장소 루트)는 중소기업용 Biz-DNA이며, 루트 `CLAUDE.md`는 중소경영 제품에만 적용된다(루트 13장). `sosang/` 아래에서는 이 파일이 우선한다. 아직 PRD가 없으므로 **이 파일이 요구사항의 정본**이다. 설계의 출처는 ChatGPT 대화(https://chatgpt.com/share/6b03f3a9-3504-83ee-9ab9-1015596447fb, 2026-11-02 시작)의 소상공인 부분이며, 그 내용을 2026-11-23에 정리했다. PRD를 따로 만들면 PRD를 정본으로 바꾸고 이 문장을 고친다. 설계를 바꾸는 결정이 생기면 이 파일의 해당 절과 9장 "미결정 사항"을 함께 갱신한다.

자매 프로젝트인 중소기업용 Biz-DNA(저장소 루트, 이하 "중소경영")의 구조·원칙을 많이 빌려 왔다. 두 프로젝트는 **대상·문항·유형 코드·전략군이 서로 다르다.** 이름이 같은 개념(DNA, 8대 역량, ST01~ST12)이 있어도 내용을 섞지 않는다.

## 1. 프로젝트 개요

- **서비스**: Biz-DNA 소상공인 경영진단(가칭). 소상공인 점주가 스마트폰·PC에서 **자기 점포를 스스로 진단**하고 다음 다섯 가지에 답을 얻는 웹서비스다.
  1. 우리 가게는 어떤 경영유형인가? (DNA 16유형)
  2. 경영역량은 어느 수준이고 강점·취약점은 무엇인가? (8대 역량)
  3. 매출·수익성이 부진하다면 원인은 무엇인가? (재무·경영위험, 상권 비교)
  4. 무엇을 먼저 해야 하는가? (우선 개선전략 3개, 30·60·90일 실행계획)
  5. 개선 후 성과는 얼마나 바뀌었는가? (재진단·성과추적, 2차 이후)
- **핵심 원칙**: 점주가 이해하기 어려운 컨설팅 용어를 줄이고, 결과는 **"우리 가게의 문제는 무엇인가?"와 "내일부터 무엇을 해야 하는가?"**를 중심으로 보여 준다.
- **흐름 (1차)**: 업종 선택 → 점포 기본정보 → 매출·비용 입력 → DNA 유형진단 → 8대 경영역량 진단 → 경영모델·영업방식 특화진단 → 결과(유형·점수·강점·취약점·위험) → 맞춤형 개선전략 3개 → 90일 실행계획 → 보고서(PDF).
- **사용자 (1차)**: 점주(주 사용자), 시스템 관리자. 컨설턴트·운영기관·수행기관 등은 3단계 확장(8장)에서 다룬다.
- **초기 대상 업종**: 13장의 7개 대분류 전체를 선택지로 두되, 진단모형 검증은 외식(음식·음료)·소매·생활서비스부터 한다. 소규모 제조·가공업은 이후 확장 대상이다.
- **범위 밖(지금은 구현 금지)**: 지원사업 신청·선정·지원자격 판정, 지원금·예산 정산, 외부 카드매출·상권 데이터 자동 연계(API 계약 전), 비교 상권 평균·통계를 지어내 보여 주기, AI가 점수·유형·전략을 직접 산출하는 것.
- **문서 언어**: UI 문구, 주석, 커밋 메시지, 문서는 한국어. 코드 식별자(변수·함수·테이블명)는 영어.

## 3. 사이트 개설 방침과 기술 스택 (2026-11-23 확정)

### 3.1 결정 (사용자, 2026-11-23)

- **소상공인 경영진단 사이트를 새로 개설한다.** 디자인·기능·서버·DB는 **중소경영(저장소 루트)의 것을 그대로 차용**한다. 바꾸는 것은 진단 내용(4장의 문항·엔진·업종분류)과 메인 색뿐이다.
- **메인 색은 `#17733b`(초록)**이다. 중소경영의 메인 색(블루 `#0071e3`)이 쓰이던 자리를 모두 이 색으로 바꾼다(7장).
- **나중에 중소경영 진단과 소상공인 진단을 한 사이트, 같은 URL(도메인)에서 합친다.** 합칠 때 코드·경로·DB가 충돌하지 않게 처음부터 3.3의 규칙을 지킨다.
- **(2026-11-23 추가 결정) 서버 DB와 배포 프로젝트는 중소경영과 같이 쓰고, 회원 계정은 구분한다.**
  - DB: 중소경영의 Supabase 프로젝트 `MBTI`(ref `jjjgyzmdqnskxussdhte`, 뭄바이 리전)를 같이 쓴다. 리전 이전을 제안하지 않는다(루트 `docs/infra.md` 11.2).
  - 배포: 중소경영의 Vercel 프로젝트 `21111/mbti-for-enterprise`를 같이 쓴다. 그래서 소상공인 코드는 같은 저장소의 `sosang/`에 두고(B안), 루트 `vercel.json` `services`에 `sosang-web`(root `sosang/web`)·`sosang-api`(root `sosang/api`)를 추가해 `/sosang/*`·`/api/sosang/*`를 그쪽으로 보낸다. `/api/sosang/(.*)` 규칙은 중소경영의 `/api/(.*)`보다 **앞에** 둔다. 소상공인 Next.js 앱은 `basePath: "/sosang"`으로 둔다. `vercel.json` 수정은 중소경영 운영 배포에 영향을 주므로 사용자 확인 후 하고, 작성 전 Vercel Services 최신 문서를 확인한다.
  - 계정: 같은 Supabase Auth 안에서 **두 서비스의 회원을 분리**한다(3.4).

- **차용 방법**: 루트(중소경영)의 파일을 `sosang/` 아래로 **복사해서 고쳐 쓴다.** 같은 저장소라도 `sosang/` 코드가 루트 코드(`../api`, `../web`)를 import하거나 심볼릭 링크로 참조하지 않고, 루트 코드도 `sosang/`를 참조하지 않는다(한쪽 수정이 다른 제품을 깨뜨리지 않게). 예외는 루트 `vercel.json`, `supabase/migrations/`, `.gitignore`·`.vercelignore`처럼 저장소에 하나뿐인 파일이다. 그대로 가져올 것: 디렉터리 구조, 디자인 시스템(`docs/design-system.md`, `globals.css`, `styles/*.css`, 공통 컴포넌트), 회원가입·로그인·마이페이지·게스트 흐름, 중간저장, 결과 대시보드·PDF 구성, 관리자 화면(`/admin`), 분석 저장소(12장), Supabase 마이그레이션·RLS 패턴, `vercel.json`, `run_dev.bat`, 스크립트(`migrate.py`, `grant_admin.py` 등).
- **가져오지 않을 것**: 중소경영의 문항·DNA 지문·유형명·전략·엔진 기준 사례(4장과 섞지 않는다), 중소경영 `.env*`·`.vercel/`(비밀값·프로젝트 연결 정보), 중소경영 `legacy/`, 중소기업 대상 문구.
- 복사한 뒤 중소경영 쪽이 고쳐지면 자동으로 따라오지 않는다. 공통 부분(인증·디자인)을 고칠 때는 어느 쪽을 먼저 고쳤는지 커밋 메시지에 남긴다. 커밋 메시지에 `[sosang]` 접두어를 붙여 중소경영 커밋과 구분한다.
- **Next.js 16은 학습 데이터와 다르다.** 코드를 쓰기 전에 설치된 `sosang/web/node_modules/next/dist/docs/`의 문서를 확인한다(중소경영 `web/AGENTS.md`와 같다).

### 3.3 통합 대비 규칙 (같은 URL로 합칠 때 충돌 방지)

저장소·DB·배포는 이미 같이 쓰고(3.1) 계정은 분리한다(3.4). 아래 규칙은 같은 도메인·같은 DB에서 두 제품이 부딪히지 않게 하는 것이다.

| 항목 | 규칙 (중소경영과 다르게) | 이유 |
| --- | --- | --- |
| 웹 경로 | 소상공인 화면은 경로 접두어 아래에 둔다(제안 `/sosang/...`, 9장 확정). 단독 운영 중에는 `/`에서 접두어로 이동시킨다 | 같은 도메인에서 중소경영 `/diagnosis`, `/mypage` 등과 겹치지 않게 |
| API 경로 | `/api/sosang/*` | 중소경영 api가 `/api/*` 전체를 쓰고 있다 |
| Python 패키지 | `sosang_api`, `engine/sosang` | `bizdna_api`, `engine/bizdna`와 한 번들에 들어가도 충돌 없게 |
| 브라우저 저장 키 | `sosang.` 접두어 (예: `sosang.survey.v1`) | 중소경영 `bizdna.survey.v1`과 같은 출처(origin)에서 섞이지 않게 |
| DB | 소상공인 테이블은 모두 **`sosang` 스키마**에 둔다(`sosang.profiles`, `sosang.consents`, `sosang.memberships`, `sosang.stores`, `sosang.assessments` …). 분석 저장소는 `sosang_analytics`·`sosang_private`. 중소경영의 `public`·`analytics`·`private` 스키마 객체를 만들거나 바꾸지 않는다(3.4의 트리거 수정만 예외) | 같은 DB에서 `profiles`·`consents` 등이 겹치지 않게 |
| 마이그레이션 | 루트 `supabase/migrations/`에 같이 두고(`scripts/migrate.py`가 이 폴더만 읽는다) 파일 이름에 `_sosang_`을 넣는다(예: `20261124000000_sosang_auth.sql`). 버전(시각)이 기존 파일과 겹치지 않게 한다. 운영 DB에 적용되므로 적용 전 사용자 확인 | 두 제품이 한 DB·한 기록표(`supabase_migrations.schema_migrations`)를 쓴다 |
| 인증·동의 | 테이블 구조는 중소경영과 같게(스키마만 `sosang`) 두되 계정은 분리한다(3.4) | |
| 색 | 메인 색을 CSS 변수 하나(`--accent`)로만 쓰고 색값을 컴포넌트에 직접 쓰지 않는다 | 합친 뒤 진단 종류별로 블루/초록을 바꿔 끼우게 |
| 버전·설정 | 설정 파일·결과의 버전 문자열에 `sosang-` 접두어 | 합친 DB에서 어느 진단 모형인지 구분 |

- 서비스명·로고 문구는 설정값으로 둔다(9장 서비스명 미정). 로고 마크는 중소경영 `Logo.tsx`를 복사해 메인 색만 바꾸고, `web/app/icon.svg`도 함께 바꾼다.

### 3.4 회원 계정 분리 (같은 Supabase Auth 안에서)

Supabase 프로젝트 하나에는 계정 풀(`auth.users`)이 하나뿐이다. 그대로 두면 한쪽에서 가입한 계정으로 다른 쪽에 로그인할 수 있고, 같은 도메인이라 로그인 쿠키도 섞인다. 다음을 **모두** 지킨다.

| 항목 | 규칙 |
| --- | --- |
| 내부 주소 도메인 | 소상공인은 `{아이디}@users.sosang.invalid` (중소경영은 `@users.bizdna.invalid`). 그래서 같은 아이디를 양쪽에서 따로 가입할 수 있다. 아이디 규칙(소문자 시작, 4~20자)은 중소경영과 같다 |
| 서비스 표시 | 가입 API(서버, admin API)가 `app_metadata.service = "sosang"`을 넣는다. `user_metadata`는 사용자가 바꿀 수 있으므로 권한 판단에 쓰지 않는다 |
| API 검사 | 소상공인 API는 JWT를 검증한 뒤 `app_metadata.service == "sosang"`이고 `sosang.profiles`에 행이 있는 사용자만 받는다. 아니면 401/403. 권한 테스트에 "중소경영 계정으로 소상공인 API 호출 → 거부"를 넣는다 |
| 로그인 쿠키 | `@supabase/ssr` 클라이언트(브라우저·서버·`proxy.ts` 모두)에 `cookieOptions.name`을 따로 준다(예: `sb-sosang-auth-token`). 기본 이름(`sb-<ref>-auth-token`)은 중소경영이 쓰므로 그대로 두면 한쪽 로그인·로그아웃이 다른 쪽에 영향을 준다. 코드 작성 전 설치된 `@supabase/ssr` 문서로 옵션을 다시 확인한다 |
| 가입 트리거 | 중소경영의 `public.handle_new_user()` 트리거는 **모든** 새 계정에 `public.profiles`·`public.consents` 행을 만든다. 소상공인 가입 전에 이 트리거를 나눠(구현: `app_metadata`는 가입 API가 INSERT 뒤에 넣을 수 있어 확실히 함께 들어오는 **내부 주소 도메인 `@users.sosang.invalid`**로 나눴다, 2026-11-24), 소상공인 계정은 `sosang.profiles`·`sosang.consents`에만 쓰게 고친다(중소경영 계정 동작은 그대로). 이 수정은 루트 `supabase/migrations/`의 새 마이그레이션으로 하고 사용자 확인 후 적용한다 |
| 중소경영 쪽 차단 | 중소경영 API도 소상공인 계정(`app_metadata.service == "sosang"`)을 거부하도록 고친다(지금은 JWT만 검증하므로 소상공인 계정이 중소경영에 로그인된다). **소상공인 회원가입을 열기 전에** 반드시 끝낸다. 중소경영 코드(루트 `api/`) 수정이므로 사용자 확인 후 진행한다 |
| 관리자 | 소상공인 관리자는 `sosang.memberships`에서 따로 관리한다. 중소경영 관리자(`whoami`)가 자동으로 소상공인 관리자가 되지 않는다. `grant_admin.py`를 복사해 `sosang` 스키마용으로 고친다 |
| 브라우저 저장 | 로그아웃 시 지우는 것도 `sosang.` 키만 지운다 |

## 4. 진단모형 핵심 규칙 (구현 시 반드시 지킬 것)

모든 가중치·기준점·유형·위험 임계값은 **시범검증 전 가설값**이다. 코드에 하드코딩하지 말고 `config/` 아래 버전 관리되는 설정 파일(`model_v1.json`, `questions_v1.json`, `industries_v1.json`)로 둔다. 결과마다 모형·문항·업종분류 버전을 함께 저장해 과거 진단을 재현할 수 있게 한다.

### 4.1 문항 구성 (총 60문항 + 입력항목)

| 구분 | 문항 수 | 점수 반영 | 상태 |
| --- | --- | --- | --- |
| DNA 경영유형 | 16 (4축 × 4문항) | 유형 판정 | 원문 있음 (`legacy/mvp_v4/engine.py`의 `DNA`, 4.2) |
| 8대 공통 경영역량 | 32 (8영역 × 4문항) | 역량 점수 | 원문 있음 (`legacy/mvp_v4/engine.py`의 `QUESTIONS`, 4.3) |
| 업종 특화 | 12 (3영역 × 4문항, 업종별로 다름) | 해당 영역 점수에 35% 혼합 (선택 응답) | 원문 있음 (`legacy/mvp_v4/advanced.py`의 `SECTOR_QUESTIONS`, 4.3) — 외식·도소매·생활서비스 3업종만 |
| 점포 기본정보·매출·비용 | 별도 입력 | 위험·재무 분석 | 4.5 |

- 대화 안의 차이: v4는 "업종(3종)별 12문항, 3개 영역에 35% 혼합", 최종 정리본은 "업종별 특화 12문항, 해당 역량에 연결해 반영", 자가진단 v2.0(원본 없음)은 "경영모델별 4 + 영업방식별 4 = 8문항, 점수 미반영"이었다. **엔진 v1은 v4 방식(3업종 × 12문항, 35% 혼합)**을 그대로 쓴다. 13장의 20개 경영모델·영업방식으로 넓히는 것은 그다음 단계이며 방법은 9장 미결정이다.
- 척도 1~5점. 역방향 문항은 `6 − 원점수`. 역문항 여부는 문항 설정에 둔다.
- **미응답은 0점이 아니라 결측(None)**이다. 영역 점수는 응답한 문항으로 환산하고 결측 비율을 결과에 남긴다. 영역 전체가 결측이면 그 영역을 빼고 가중치를 다시 나눈다(중소경영 엔진과 같은 규칙).
- 문항이 많으므로 **업종별 분기와 문항 묶음(페이지)별 진행**으로 응답 부담을 줄이고, 중간저장을 지원한다.
- **코드 체계(제안)**: DNA `D01~D16`, 역량 `A01~H04`, 특화 `<업종>-<영역><번호>`(예: `FOOD-B01`. 업종마다 다른 문항이 같은 자리에 오므로 문항 마스터에서는 `(section, sector, code)`로 고유하게 관리). 입력 JSON은 `answers.dna`, `answers.competence`, `answers.special`로 네임스페이스를 나눈다.

### 4.2 DNA 경영유형 (4축 → 16유형)

| 축 | 키 | A 성향 | B 성향 |
| --- | --- | --- | --- |
| 경영목표 | `goal` | **G** 성장확대형 | **S** 안정생계형 |
| 경쟁전략 | `compete` | **D** 차별화형 | **E** 가격·효율형 |
| 고객전략 | `customer` | **N** 신규고객 개척형 | **R** 단골고객 중심형 |
| 운영방식 | `operation` | **P** 체계적 관리형 | **O** 점주 직접운영형 |

- **응답 방식**: 한 문항은 양 끝 문장 한 쌍이다. 점주는 "왼쪽 성향 1점 ↔ 오른쪽 성향 5점"으로 자기 점포에 가까운 쪽을 고른다. **왼쪽이 B 성향, 오른쪽이 A 성향**이며 화면에 "두 방향에 우열은 없습니다"를 표시한다. 지금 문항은 모두 같은 방향이라 역문항이 없다.
- **지문 16문항** (`legacy/mvp_v4/engine.py`의 `DNA` 원문, mvp_integrated와 같다. 코드는 이 프로젝트에서 붙인 제안):

| 코드 | 축 | 왼쪽 (1점, B) | 오른쪽 (5점, A) |
| --- | --- | --- | --- |
| D01 | 경영목표 S↔G | 안정적 수익 유지 | 매출 확대를 위한 투자 |
| D02 | 경영목표 S↔G | 현재 규모 유지 | 사업규모 확대 |
| D03 | 경영목표 S↔G | 안정적 운영 | 성장기회 선점 |
| D04 | 경영목표 S↔G | 재무안정 우선 | 성장투자 우선 |
| D05 | 경쟁전략 E↔D | 가격·운영효율 | 차별화된 고객경험 |
| D06 | 경쟁전략 E↔D | 비용 절감 | 상품 혁신 |
| D07 | 경쟁전략 E↔D | 표준상품 중심 | 특화상품 중심 |
| D08 | 경쟁전략 E↔D | 운영 생산성 | 브랜드 차별성 |
| D09 | 고객전략 R↔N | 단골고객 심화 | 신규고객 확대 |
| D10 | 고객전략 R↔N | 기존 상권 집중 | 신규 상권·채널 개척 |
| D11 | 고객전략 R↔N | 기존 고객 유지 | 새로운 고객군 발굴 |
| D12 | 고객전략 R↔N | 재방문 관리 | 신규고객 유입 |

| D15 | 운영방식 O↔P | 점주 직접 고객응대 | 표준화된 고객관리 |
| D16 | 운영방식 O↔P | 개인 판단 중심 | 역할분담 중심 |

- 축 점수: `D_k = Σ(x_kj − 1) / (4 × 4) × 100` (축별 4문항, 0~100, 높을수록 A 성향). MVP의 축 키는 `G/S`·`D/E`·`N/R`·`P/O`이고, 이 프로젝트에서는 `goal`·`compete`·`customer`·`operation`으로 바꾼다.
- 판정(가설값): 4자리 코드는 **50 이상이면 A 문자**로 정하고, 40 초과 60 미만인 축은 **경계**로 따로 표시한다("유형은 잠정 판정"). v4·통합판의 규칙과 같다. 60 이상 A 성향, 40 이하 B 성향으로 부른다.
- 유형 코드 순서는 항상 `[G|S][D|E][N|R][P|O]`.

### 4.4 업종 분류 (13장 상세)

- **진단모형의 단위는 세부업종이 아니라 "경영모델"이다.** 7개 대분류 → 20개 경영모델 → 세부업종 → 주된 영업방식의 다층 구조로 받는다.
- 한식·중식·일식처럼 세부업종이 달라도 경영모델이 같으면 같은 진단모형(문항·가중치)을 쓴다. 세부업종은 표시용에 그치지 않고, 특정 업종에만 필요한 추가문항이나 전략 규칙을 거는 데 쓴다.
- 진단모형 = **공통진단 + 경영모델 특화진단 + 영업방식(운영방식) 보정**.
- 업종분류는 Biz-DNA 자체 분류이며 한국표준산업분류와 일대일 대응하지 않는다. KSIC 코드 매핑은 나중에 속성으로 추가한다.

### 4.5 점포 정보·재무 입력과 경영위험

**입력항목**: 점포명, 업종(대분류·경영모델·세부업종·영업방식), 지역, 종사자 수, 경영방식 속성(13.3), 월평균 매출, 원재료·매입비, 인건비, 임대료, 기타비용(금액 단위 만원/월, v4와 같음).
- **우선 경영목표**(필수, 하나, v4): 수익성 개선 · 매출확대 · 단골확보 · 운영효율 · 사업전환. 전략 적합성에 쓴다(4.6).
- **성장단계 판단용 실적자료**(선택, v4): 운영기간(개월), 재방문 고객 비율(%), 최근 12개월 흑자월 수(0~12), 판매채널 수, 직원 수, 전년 동월 매출(만원). 성장단계(4.7)와 매출증감률에 쓴다.
- **비교기준 월매출**(선택, v4): 사용자가 직접 넣는 참고값. 결과에 "사용자 제공 참고값이며 공식 업종 평균으로 검증되지 않음"을 붙인다. 공식 평균처럼 보여 주지 않는다.

**파생값**:
- `영업잔여액 = 월매출 − (원재료·매입비 + 인건비 + 임대료 + 기타비용)`. **세무·회계상 영업이익이 아니다.** 화면·보고서에 그렇게 표시한다.
- `임대료 비율 = 임대료 / 월매출`, `원가율`, `인건비율`, `전년 동월 대비 매출증감률`.

**위험 규칙 (가설값, 설정 파일로)**. 코드는 v4 `engine.py`의 것을 그대로 쓴다.

| 코드 | 수준 | 위험 | 판정 (초기값) | 효과 |
| --- | --- | --- | --- | --- |
| NO_SALES | high | 매출 없음 | 월매출 = 0 | 수익성·임대료 비율 산정 불가 표시 |
| NEGATIVE_CASH | high | 영업잔여액 적자 | 영업잔여액 < 0 | 재무·수익 전략을 최우선, 확장·마케팅 투자는 후순위 |
| RENT_BURDEN | medium | 임대료 부담 | 임대료 비율 > 20% | 재무·수익 전략 적합성 가산, 고정비 점검 |
| LOW_BUFFER | medium | 여유자금 부족 | 월매출 > 0 이고 총비용 > 월매출 × 95% | 경고만 (v4에서 추가) |
| WEAK_FINANCE | medium | 재무역량 취약 | 재무·수익 영역 점수 < 40 | 원가·현금흐름 점검 |

- 적자 기준: v4·통합판은 `< 0`, 첫 MVP(`mvp_v1`)는 `≤ 0`이었다. v4를 따르되 0인 경우의 처리는 9장에서 확정한다.
- 최종 설계는 "업종 공통 임계값 하나보다 업종·점포규모·비용구조·시계열 추세를 고려"하라고 했다. 그래서 임계값을 **경영모델별로 덮어쓸 수 있는 설정 구조**로 만든다.
- 입력 검증(v4): 금액은 유한한 0 이상 숫자, 임대료는 총비용 이하, 재방문율 0~100, 흑자월 수 0~12. v4는 비용을 "총비용(임대료 포함)" 한 칸으로 받았다. 이 프로젝트는 비용을 항목별(원재료·매입비, 인건비, 임대료, 기타)로 받고 합계를 계산한다.
- 고객이탈·운영비효율·디지털 취약 위험은 재방문율·재고회전 같은 실적 입력이 생기면 추가한다.

| ST12 | 사업전환·재도약 | 사업모델 재설계·업종전환 검토 |

- 우선순위 점수 `R_j = 0.35U + 0.30F + 0.20E + 0.15X` (각 0~100). U 개선시급성(취약역량·위험의 심각도), F 전략적합성(업종·DNA 유형·경영목표), E 기대효과, X 실행가능성(비용·인력·기간·점주 여건). 대화 중간(v3)에는 `0.45U + 0.35F + 0.20X`였으나 최종 설계를 따른다.
- **"점수 낮은 영역 = 추천"이 아니다.** 문제의 심각성·목표·실행가능성·효과를 함께 본다. 필수 규칙이 가중점수보다 우선한다(예: 적자·현금흐름 불안정 점포에는 설비투자·2호점 확대(ST11)보다 수익구조 개선(ST01·ST02)을 먼저. 수익이 안정적이고 수요가 늘면 판로확장·운영강화를 추천할 수 있다).
- U·F·E·X를 12전략별로 어떻게 계산할지(전략 ↔ 연계 역량·위험·목표·DNA 유형 매칭 매트릭스)는 **아직 없다.** 8장 2번 설계 산출물이다.
- **엔진 v1(임시)은 v4 알고리즘(`engine.diagnose` → `advanced.diagnose_v4`)을 그대로 재현한다.** 12전략 대신 **8개 영역별 전략**을 쓴다. 결과에는 "임시 규칙"임을 표시하고, 매트릭스가 나오면 하나씩 바꾼다(중소경영이 1.0 엔진을 먼저 재현한 방식과 같다).

| 영역 | 전략명 | 실행과제 | 성과지표 |
| --- | --- | --- | --- |
| 재무·수익 | 수익구조 및 현금흐름 개선 | 상품별 공헌이익과 고정비를 점검하고 13주 현금흐름표 작성 | 영업현금수지·상품별 마진 |
| 상권·입지 | 상권수요 대응 및 입지전략 | 시간대별 수요와 경쟁점포를 분석해 상품·영업시간 재설계 | 시간대별 매출·유입고객 |
| 상품·서비스 | 주력상품 경쟁력 강화 | 고객평가를 반영하고 저수익 상품을 정비 | 주력상품 재구매율·마진 |
| 고객관리 | 단골고객 및 재방문 확대 | 재방문율을 측정하고 고객불만 개선·단골 프로그램 실행 | 재방문율·고객만족 |
| 마케팅·판로 | 신규고객 유입 강화 | 지도·리뷰·SNS 노출을 정비하고 유입경로별 성과 측정 | 신규고객 수·채널별 전환율 |
| 점포운영 | 점포 운영효율 개선 | 발주·재고·서비스 매뉴얼을 표준화하고 낭비시간 절감 | 재고회전·폐기율·처리시간 |
| 디지털 | 디지털 경영관리 도입 | POS·매출자료를 정리하고 반복업무를 자동화 | 데이터 기록률·업무시간 |
| 경영자·미래대응 | 경영목표 및 대응계획 수립 | 분기 목표·우선 실행과제·매출악화 대응계획 마련 | 월별 목표달성률·위험대응 실행률 |

  - 시급성 `U = 100 − 영역 점수`
  - 적합성 `F = 50 + 업종 가산점 × 4`. 가산점: 외식업 {재무·수익 6, 상품·서비스 4, 고객관리 3}, 도소매업 {재무·수익 5, 점포운영 5, 상권·입지 3}, 생활서비스업 {고객관리 6, 점포운영 4, 마케팅·판로 3}, 기타 없음
  - 규칙(순서대로): 적자면 재무·수익 `F = 100`, `U = max(U, 95)`이고 마케팅·판로 `F = 20` / 임대료 비율 > 20%면 재무·수익 `F = min(100, F + 15)` / 외식업이면 점포운영 `F += 8` / **우선 경영목표에 연결된 영역 `F = min(100, F + 18)`** (수익성 개선→재무·수익, 매출확대→마케팅·판로, 단골확보→고객관리, 운영효율→점포운영, 사업전환→경영자·미래대응. 목표가 없으면 수익성 개선)
  - 실행가능성 `X = 70` (상권·입지·디지털은 60)
  - 우선점수 `= 0.45U + 0.35F + 0.20X` (대화 v3식). **적자면 마케팅·판로와 상권·입지의 우선점수를 35 이하로 제한**하고 "적자상태로 확장성 지출 우선순위 제한"을 근거에 남긴다(`gated`).
  - 공통 점수로 우선점수를 매겨 내림차순(같으면 영역명 순) **상위 5개를 먼저 고른 뒤**, 특화점수(4.3)를 반영한 점수로 그 5개의 `U`와 우선점수를 다시 계산해 다시 정렬한다. 즉 특화문항 때문에 6위 이하 영역이 5위 안으로 들어오지는 않는다. **기준 사례 재현을 위해 이 동작을 그대로 따르되**, 엔진 v2에서 "특화 반영 후 8개 전체를 정렬"로 고칠지 9장에서 정한다.
  - 1~3순위를 우선전략으로 보여 준다. 전략마다 근거 문장("역량 ○점, 격차 ○점, 적합도 ○점, 실행가능성 ○점")을 남긴다.
  - 강점·보완 영역: (특화 반영 후) 점수 상위 2개, 하위 2개.
  - v4의 업종은 4종(외식업·도소매업·생활서비스업·기타)뿐이다. 표에 없는 업종은 "기타"로 본다. 13장의 경영모델로 옮길 때 대분류 FOOD → 외식업, RETAIL·WHOLESALE → 도소매업, LIFE → 생활서비스업, 나머지 → 기타로 임시 대응시킨다(9장 확정 필요).
- 전략마다 **순위, 점수와 4요소, 선정 근거(연계 문항·위험 ID), 적용된 규칙 ID, 실행과제와 추진방법, 권장 기간·필요 자원, 성과지표**를 결과에 저장한다(추적 가능성).
- 실행계획은 30·60·90일 단위로 제시하고, 정밀형에서는 1~3년 로드맵까지 쓴다.

### 4.7 성장단계 (v4 잠정 규칙)

- **운영기간, 재방문율, 최근 12개월 흑자월 수가 모두 있을 때만** 잠정 판정한다. 하나라도 없으면 `UNDETERMINED`("성장단계 미판정", 필수 증빙 미입력). 업력만으로 단계를 정하지 않는다.
- 매출증감률 `= (월매출 / 전년 동월 매출 − 1) × 100` (전년 동월 매출이 있을 때만).
- 판정(가설값, 위에서부터 처음 맞는 것):

| 조건 | 단계 |
| --- | --- |
| 운영기간 < 6개월 또는 재방문율 < 10% | S1 시장검증기 |
| 운영기간 < 12개월 또는 재방문율 < 25% | S2 사업기반 구축기 |
| 흑자월 < 9 또는 매출증감률 없음 | S3 안정운영기 |
| 매출증감률 ≥ 15% 이고 판매채널 ≥ 2 이고 직원 ≥ 2 | S4 성장확장기 |
| 그 밖 | S3 안정운영기 |

- **S5 규모화·전환기는 이 입력으로는 판정하지 않는다.** 결과에는 "입력된 운영기간·재방문·흑자월수·매출추세에 따른 잠정 판정"을 붙인다.
- 단계는 지금 전략 점수에 쓰이지 않는다(표시용). 전략과 연결할지는 9장.
- **진단 신뢰도**(v4): 성장단계가 판정되고 특화 3개 영역을 모두 답했으면 "보통", 아니면 "제한적". 근거 개수(입력된 실적 항목 수)와 "자가응답 기반. 외부 카드매출·상권 데이터 검증 전 단계"를 함께 표시한다.
- Biz-DNA 3.0 설계는 "사업화·안정화·확장·전환" 단계를 언급했다. v4 단계명과 맞출지는 9장.

### 4.8 상권 비교 분석 (2차 이후)

- `GAP = 점포 매출 변화율 − 비교 상권(동일 업종) 매출 변화율`. 예: 점포 −10%, 상권 +5% → GAP −15%p → "상권 대비 상대적 부진 가능성" 표시.
- GAP만으로 원인을 단정하지 않는다. 원인 판단에는 경쟁점포, 고객 변화, 영업일수, 상품구성 등 추가 자료를 쓴다.
- **실제 상권 데이터가 없으면 비교 점수나 평균을 임의로 만들지 않는다.** 1차에서는 이 기능을 넣지 않고, 2차에서 CSV 업로드 방식(대화 v5)부터 검토한다. 외부 카드매출 API는 데이터 제공 계약 이후다.

## 5. AI 사용 규칙

- 점수·유형·위험·전략은 **엔진만** 산출한다. AI는 엔진 결과를 해석·서술하고 실행계획을 구체화만 한다.
- AI가 확인되지 않은 매출·재무 실적, 상권 평균, 개선효과를 만들어 내지 않는다. 보고서에는 **실제 측정값 · 점주 자기평가 · 분석 가설 · 향후 목표값**을 구분해 표시한다.
- 원인 분석은 "가설"로 쓴다. 점수가 낮다는 이유만으로 원인을 사실처럼 쓰지 않는다.
- 사용자 동의가 없거나 API 키가 없으면 규칙기반 보고서만 만든다(AI 없이도 전 기능 동작).
- AI에는 해석에 필요한 진단결과만 보내고 점포명·주소·연락처 등 식별정보는 보내지 않는다.
- AI 공급자는 미정. 교체가 쉽도록 어댑터 인터페이스 뒤에 둔다.

## 6. 보안·데이터

- 점포의 매출·비용은 민감한 경영정보다. **인증·권한·암호화가 갖춰지기 전에는 실제 점포 데이터를 받지 않는다**(테스트는 가상 점포만). 대화의 v6~v8도 같은 이유로 공개 버전에서 저장 기능을 뺐다.
- 접근권한: 점주는 자기 점포만. 운영기관·컨설턴트가 생기면 담당 범위만(3단계). **모든 조회 API에 권한 필터를 서버측에서** 적용하고 권한 테스트를 함께 작성한다.
- 집계 통계는 비식별 처리하고, 표본이 작은 칸은 숨긴다(12장). 운영기관 통계는 "진단에 참여한 점포 기준"임을 표시한다. 상권 전체를 대표하려면 별도 표본설계가 필요하다.
- 개인정보 수집·이용, 결과 저장, 통계 활용, AI 분석 동의를 따로 기록한다. 보존기간·파기 정책을 개인정보처리방침에 정하고 그대로 구현한다.
- 비밀키·API 키는 `.env`에만 두고 커밋하지 않는다. 커밋하는 것은 `.env.example`뿐이다. `NEXT_PUBLIC_` 변수에 비밀값을 넣지 않는다.

## 8. 개발 우선순위

1. **엔진 v1 = v4 재현**: DNA 16·역량 32·업종 특화 12문항, 업종별 가중치, 위험 5개, 4.6의 임시 전략 알고리즘, 4.7의 잠정 성장단계로 엔진을 만들고 4.9 기준 사례 4개와 v4 테스트 시나리오를 통과시킨다. 이것만으로 1차 MVP의 진단 핵심이 돌아간다.
2. **설계 산출물** (엔진을 최종 설계로 바꾸는 데 필요): ① 12전략 매칭 매트릭스(U·F·E·X 계산과 필수 규칙), ② 20개 경영모델·영업방식용 특화문항(v4의 3업종 문항에서 출발), ③ 경영모델별 가중치(처음엔 소속 업종의 v4 값), ④ 문항 채점기준표(역문항, 결측). 대화·MVP에 없는 내용은 임의로 확정하지 말고 `draft: true` 초안으로 만들어 사용자에게 확인받는다.
3. **1차 MVP (점주 자가진단)**: 업종 선택, 점포정보·재무 입력, 60문항 진단, 유형·역량·위험·전략추천, 30·60·90일 실행계획, 결과 화면, **기본형 PDF(5~6쪽)**, 회원(진단 이력 저장)·게스트(브라우저 저장).
4. **2차 고도화**: AI 정밀보고서(20~24쪽, 14장 목차), 재진단·진단 전후 비교, 개선과제 등록·이행관리, 월별 실적 입력·성과추적, 상권 비교(CSV), 운영기관 대시보드(상권·업종별 집계).
5. **3차 확장 (Biz-DNA 3.0)**: 소상공인 지원사업 진단·컨설팅·성과관리 통합 플랫폼(15장). 실제 상권 빅데이터, 지원프로그램 매칭, 비교집단 기반 정책효과 분석.

기능을 구현할 때 커밋·PR 설명에 기능 ID를 적는다(FR ID 체계는 PRD를 만들 때 정한다. 그 전에는 이 파일의 절 번호를 쓴다. 예: `4.5 NEGATIVE_CASH 적자 위험 규칙`).

## 11. DB·인증·배포

중소경영 11장(루트 `docs/infra.md`)의 설계와 구현을 그대로 차용한다(2026-11-23 결정, 3.1). 요점만 적는다. 이름·경로·스키마는 3.3의 통합 대비 규칙을 따른다. **Supabase 프로젝트 `MBTI`와 Vercel 프로젝트 `mbti-for-enterprise`를 중소경영과 같이 쓰고, 회원 계정은 분리한다**(2026-11-23, 3.1·3.4).

- 그 DB는 **중소경영이 실제 운영 중인 DB**다. 소상공인 작업은 `sosang*` 스키마 안에서만 하고, 중소경영 객체를 바꾸는 작업(3.4 가입 트리거)과 마이그레이션 적용·환경변수 변경·운영 배포는 매번 사용자 확인을 받는다.
- 환경변수는 중소경영 것을 같이 쓴다(`SUPABASE_URL`, `SUPABASE_SECRET_KEY`, `POSTGRES_URL` 등, Production 전용). 소상공인 전용 값이 필요하면 `SOSANG_` 접두어로 추가한다. 로컬에서는 루트 `api/.env`를 `sosang/api/.env`로 복사해 쓴다(커밋 금지, 루트 `.gitignore`의 `.env` 규칙이 적용된다).
- 미리보기(Preview) 배포에는 Supabase 환경변수가 없어 게스트 진단만 된다(루트 `docs/infra.md` 11.2와 같다).
- 소상공인 웹은 중소경영과 같은 `NEXT_PUBLIC_SUPABASE_URL`·`NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`를, 소상공인 API는 같은 `SUPABASE_URL`·`SUPABASE_SECRET_KEY`·`POSTGRES_URL`(·`SUPABASE_JWT_SECRET`)을 읽는다. 로그인 세션 갱신용 `proxy.ts`는 두지 않았다(브라우저 클라이언트가 토큰을 갱신하고, 마이페이지는 화면에서 로그인 여부를 확인한다).
- 아래 11.1의 테이블은 모두 `sosang` 스키마에 둔다.

- 브라우저는 Supabase를 **로그인에만** 쓰고, 점포·진단 데이터의 읽기·쓰기는 모두 FastAPI를 거친다. 모든 테이블에 RLS를 켠다.
- API는 Supabase JWT를 공개 서명 키(JWKS)로 검증한다. 역할은 사용자가 바꿀 수 없는 곳(`memberships` 테이블 또는 `app_metadata`)에 둔다.
- 스키마·RLS·트리거는 `supabase/migrations/*.sql`로 남긴다. 대시보드에서 손으로 바꾸지 않는다.
- 회원은 단계를 넘길 때·"중간저장" 때 서버에 `draft`로, 진단을 마치면 엔진 결과와 버전을 함께 저장한다. 게스트는 브라우저에만 저장한다.

- 문항·가중치·업종분류의 정본은 처음에는 `config/*.json`이다. 관리자 화면에서 바꾸는 기능이 생길 때 DB로 옮길지 정한다.
- 3차(15장)에서는 점포 마스터와 사업참여 이력을 분리한다(`businesses` : `program_participations` = 1 : N).

## 12. 경영자 성향 데이터 수집 (분석 저장소, 2차)

중소경영 12장(루트 `docs/analytics-store.md`)의 설계(2026-11-18 확정)를 기본으로 따른다. 차이만 적는다.

- **원본과 분석용을 나눈다.** `assessments`가 원본이고, 분석 행은 최종저장 시점에 통계 활용에 동의한 회원의 회차만 파생한다(`derive_rows(assessment, *, subject_key, round_no)` 순수 함수, 같은 트랜잭션에서 upsert). 게스트는 넣지 않는다.
- **화이트리스트로만 꺼낸다.** 점포명, 주소·지역의 상세 부분, 자유서술, 회원 ID는 넣지 않는다. 사람은 `private.subject_map`의 가명키로만 잇는다.
- **DNA 성향은 4축 방향값으로 저장한다.** `방향값 = (축 점수 − 50) × 2` (−100~+100, `+`는 G·D·N·P, `−`는 S·E·R·O). 역산: `축 점수 = 50 + 방향값 / 2`. 유형 문자·경계 여부는 저장하지 않고 그 회차 모형 버전의 기준값으로 조회 시 계산한다. 축별 4문항이라 축 점수는 6.25 단위이며 방향값은 `numeric(5,2)`에서 정확하다. 컬럼: `dna_goal_dir`, `dna_compete_dir`, `dna_customer_dir`, `dna_operation_dir`와 축별 응답 수.
- **그 밖의 값은 원값 그대로** 저장한다(업종 4단계 코드, 영업방식·경영방식 속성, 종사자 수, 업력, 월매출·비용 항목, 파생 비율, 영역 점수, 종합점수·등급, 위험 ID, 전략 점수·순위). 문항 단위 응답은 저장하지 않는다(필요하면 원본에서 백필).
- 화면·보고서·운영기관에는 **집계만** 낸다. 구간(매출·종사자 등)은 집계 단계에서만 쓰고, 표본이 `k`(가설값 5) 미만인 칸은 API에서 숨긴다.
- 지역은 시·군·구 수준까지만 분석 저장소에 넣는다(상권 집계용). 더 좁은 단위는 9장에서 정한다.

## 14. 자동 보고서

- **기본형 (5~6쪽, 1차)**: 점포현황, DNA 유형, 종합점수·등급, 8대 역량, 매출·비용 구조와 위험 신호, 핵심 취약점, 3대 개선전략, 30·60·90일 실행계획.
- **AI 정밀형 (20~24쪽, 2차)**:

| 장 | 내용 | 분량 |
| --- | --- | --- |
| Ⅰ | 점포현황 및 종합진단 (종합의견) | 3p |
| Ⅱ | DNA 경영유형 분석 (특성·강점·약점·성장방향) | 2p |
| Ⅲ | 8대 경영역량 상세분석 (영역당 1쪽) | 8p |
| Ⅳ | 재무·수익구조 분석 (비용구조, 손익분기점, 매출 변화에 따른 영업잔여액 시뮬레이션) | 3p |
| Ⅴ | 핵심 경영문제 및 원인 가설 | 2p |
| Ⅵ | 맞춤형 경영개선 전략 (전략별 목표·세부과제·실행방법) | 3p |
| Ⅶ | 실행 로드맵 및 성과관리 (90일 계획, 1~3년 로드맵, KPI) | 3p |

- 영역별 분석은 항상 **진단결과 → 문제원인(가설) → 개선방향 → 실행과제(방법·완료목표)·성과지표** 순서로 쓴다. 핵심 문제 표는 "핵심 문제 · 진단 근거(점수·응답) · 원인 가설 · 개선전략"을 잇는다.
- 상권·입지 장은 실제 상권 데이터가 있을 때만 쓴다.
- 보고서 생성 단계: 점수 산출 → 취약영역 식별(점수 낮음 × 중요도 높음) → 문항 응답·재무자료 근거의 원인 가설 → 전략 선정 → 실행계획 → (AI) 서술 → PDF 편집.

## 15. 3단계 확장: Biz-DNA 3.0 지원사업 통합 플랫폼 (참고 설계, 지금 구현하지 않음)

1·2차 설계가 이 확장을 막지 않도록 참고로 남긴다.

- **목표**: 지원사업의 신청·선정 → 사전진단 → 맞춤형 지원설계 → 컨설팅 수행 → 개선과제 실행 → 사후진단·성과평가 → 정책환류를 한 플랫폼에서 관리한다.
- **사용자 6종**: 소상공인(본인 사업장), 전문 컨설턴트(배정 기업), 수행기관(담당 사업), 운영·발주기관(소관 사업), 평가·품질관리자(승인된 대상), 시스템 관리자. 권한 = 역할(RBAC) + 사업별 접근권한 + 기업별 담당자 배정. 운영기관과 수행기관의 역할을 분리하되 사업별로 권한 위임을 설정할 수 있게 한다.
- **10대 모듈**: M01 지원사업 관리, M02 참여기업 관리, M03 Biz-DNA 진단, M04 맞춤형 지원설계, M05 전문가 관리, M06 컨설팅 수행관리, M07 지원금·예산관리, M08 실행과제 관리, M09 성과관리·평가, M10 AI 보고서·통계. (13장 경영모델 코드 M01~M20과 다른 체계이므로, 구현할 때 모듈 코드는 `MOD01`처럼 접두어를 바꾼다.)
- **지원프로그램 매칭(가설)**: `0.30N + 0.25F + 0.20E + 0.15R + 0.10P` (N 지원 필요성, F 유형·업종·단계 적합성, E 예상 개선효과, R 실행 준비도, P 정책목표 부합성). 법적 자격 미충족·중복지원 제한·예산 부족이면 자동 선정하지 않는다. **AI 추천은 최종 선정·승인을 대체하지 않는다.**
- **실행과제 상태**: 계획 → 진행 → 검토요청 → 승인완료 (+ 보류·반려·재작업). 과제 필드: 과제명, 문제원인, 개선목표, 세부활동, 담당자, 기간, 필요자원, 성과지표, 완료기준, 증빙.
- **성과분석 3수준**: 실적관리(지원·완료·집행) → 성과변화(사전·사후·시계열) → 정책효과(비교집단·이중차분·매칭, 식별가정 검토). 전후 변화만으로 사업효과를 단정하지 않는다.
- **보고서 5종**: R01 기업진단, R02 맞춤형 지원계획서, R03 컨설팅 결과, R04 기업 성과, R05 사업 종합성과.
